The R1 picture in one line

MVP gets an officer to the door of an opportunity, with postings from OTG ingestion. R1 brings both ends in-house: agencies create opportunities directly in CareerCompass, and officers apply without leaving it. CareerCompass stops being a read-only window onto OTG and becomes the system of record.

The 5 epics

Epic A — Opportunity Creation SPINE · new 19 Jun

Agencies author and manage postings directly in CareerCompass — structured creation form, posting lives in OTEP's DB, validation + publish workflow, edit/close lifecycle. Native agency-admin capability (decided 2 Jun: creation moved R4 → R1).

Why it's a spine: flips CareerCompass into the system of record. Prerequisite that lets Internal Jobs + Secondments re-enter (pulled from MVP for lack of creation tooling). Reverses the OTEP-127 "criteria stays in OTG" posture — the ringfencing-criteria write path comes into scope.

Scope reality — 2–3x expansion. Net-new agency-admin UI + creation data model + validation/publish workflow, against Thomas as sole FE in a 3-month window. The capacity conversation, not a footnote.
Recommend: narrow creation, not all five types. Lead with Internal Jobs + Secondments only for R1 (the two with no other home post-OTG). Full 5-type (add STIP/Gig/PSFG) = stretch. Roughly halves the build, still delivers the system-of-record promise for the types that need it. Walk in with this and Adrian's strongest challenge is already answered.
SJR default: NOT in R1 creation. Excluded from MVP ingestion (21 May), apply deferred. OUT unless Mark explicitly pulls it in — don't let it default in.
Criteria authoring: recommend phasing OUT of R1 → R1.5. It reverses a logged BO decision and re-opens the POCDEX write path, currently blocked on Core (#31). Keeping it out keeps R1 off the blocker. Name it as a conscious choice, not a silent scope bomb.
Agency-admin auth — open dependency. Creation needs an agency-admin auth surface, distinct from the officer login (WOG AD) still being onboarded (#26, not approved). Who is an admin, how they authenticate, whether it's built — all undefined. Foundational to Epic A. (→ Pow Hwee / Fabian)

C@G is the exception — keep it as native as possible. Stays on its own rails (own source/integration), not authored through the generic create form.

→ Open: narrow vs full 5-type? How does "C@G as native as possible" resolve? Criteria authoring R1 or R1.5 (rec R1.5)? Agency-admin auth — exists, who owns it? (Mark / Jacky / Pow Hwee / Fabian)

Epic B — Streamlined Application SPINE

The end-to-end in-Compass apply flow. HR side: agencies post job types incl. secondments directly (distinct from the MVP interim-form workaround for OTG agencies without a formsg_url). Officer side: a full in-Compass native OTEP form — not an embedded third-party (FormSG/C@G) form. Compass owns it, pre-filled from the officer's profile, posting to OTEP's backend. No redirects, no embeds.

Why it's the apply core: the rest hangs off this — status tracking needs a submitted application, Saved Jobs needs a form to resume, Smart Assistant pre-fills this form. (Epic A is upstream — can't apply to a posting that wasn't created.)

Form architecture — decided: native OTEP form, not a FormSG/C@G embed. Was the biggest estimate driver; now settled. Remaining detail for Pow Hwee: form data model + submission posting (feeds Epic C).
Cross-squad dependency. Profile pre-fill (competencies + work history) sits on the competency SSOT owned by Imelda's squad, via an in-code interface, endpoint specs still in flight (Léo ↔ Kingsley, #18/#41). Both B's pre-fill and E's mapping ride on a contract that isn't finalised — same shape that pushed auth to S4+. Don't treat pre-fill as a given.

Epic C — Status Tracking

End-to-end application monitoring, native in OTEP. OTEP owns the state machine: submitted → under review → outcome. No ATS integration in R1 — R2 or when a vendor is confirmed.

Depends on: Epic B (need a submitted application to have a status).

→ Open (data): states? who triggers transitions? who sees status — officer only or HR too? (Pow Hwee)

Design load (not just a data model): submitted → under review → outcome is a user-facing emotional journey. The "outcome = rejection" state and the "no applications yet" empty state are real design surfaces, currently unnamed. (→ Amber)

Epic D — Saved Jobs

Officers save/bookmark opportunities and resume in-progress applications without losing data.

Why it pairs with B: "resume an application" only means something once there's an in-Compass form to half-fill. The "save an opportunity" half is lighter and could ship earlier.

→ Open: persist across sessions? what happens when a saved posting closes (expiry)? (Pow Hwee)

Epic E — Smart Assistant

Auto-populates the officer's strengths/experience fields on the form from their OTEP profile. R1 scope deliberately narrow: profile-driven pre-fill only. NOT CV-upload inference (CIE flow, OTEP-205 — separate).

Depends on: Epic B (pre-fills B's form).

Design caveat — the pre-fill interaction is load-bearing, even if the inference is cut. The pre-filled-then-editable form is a known UX trap: what does the officer see when pre-fill is wrong, partial, or stale (#18)? Separate the pre-fill interaction design (must exist in B regardless) from the smart inference (can flex to Could). Don't let cutting E leave B's core interaction undesigned.

→ Open: which profile fields map to which form fields? Field-mapping exercise. (Amber / Pow Hwee)
