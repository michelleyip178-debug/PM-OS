## The R1 picture in one line

MVP gets an officer to the *door* of an opportunity (browse, filter, view, click out to apply), and the postings come from OTG ingestion. **R1 brings both ends in-house:** agencies *create* opportunities directly in CareerCompass, and officers *apply* without leaving it — create it, post it, pre-fill it, submit it, track it, save it. CareerCompass stops being a read-only window onto OTG and becomes the system of record.

## The 5 epics

### Epic A — Opportunity Creation (new spine, added 19 Jun)

Agencies author and manage postings **directly in CareerCompass** — a structured creation form, the posting lives in OTEP's DB, validation + publish workflow, and the edit/close lifecycle. This is the native agency-admin capability (decided 2 Jun: creation moved R4 → R1; supersedes the old BO R4 direction).

**Why it's a spine, not a feature:** it flips CareerCompass from a read-only window onto OTG into the **system of record**. Two big consequences:
- It's the prerequisite that lets **Internal Jobs + Secondments re-enter** — they were pulled from MVP (17 Jun) *specifically because* there's no creation/management tooling. R1 creation is what brings them back.
- It reverses the MVP posture (OTEP-127, 17 Jun) where creation + ringfencing criteria **stay in OTG**. R1 moves authoring into Compass — so the ringfencing-criteria *write* path that we deliberately kept out of MVP comes into scope here.

**Scope reality (flag hard at the jam):** the decisions log already calls this a **2–3x scope expansion** — net-new agency-admin UI, a creation data model, and a validation/publish workflow, against Thomas as sole FE in a 3-month R1 window. This is the capacity conversation, not a footnote.

**Recommended R1 scope — narrow creation, not all five types.** Lead with **Internal Jobs + Secondments only** for R1 native creation. These are the two types with *no other home* post-OTG (they were pulled from MVP precisely because there's no creation tooling — 17 Jun). The full five-type creation set (adding STIP, Gig, PSFG) is the **stretch**, not the base. Why narrow: it roughly halves the build, it still delivers the "system of record" promise for the types that need it most, and it's the honest position given one FE in 3 months. If we walk in proposing all five, Adrian's strongest challenge ("do they *all* need creation in R1?") lands on us; if we lead with narrow, we've already answered it.

**SJR default: NOT in R1 creation.** SJR was excluded from MVP ingestion entirely (2026-05-21) and its apply flow deferred. Treat "SJR is agency-created in R1" as OUT unless Mark explicitly pulls it in — don't let it default into Epic A as an open question that quietly adds scope.

**Criteria authoring — recommend phasing OUT of R1 (named decision, not a sub-bullet).** R1 creation should ship **without** ringfencing-criteria authoring; criteria stays OTG-read (the MVP OTEP-127 posture) for R1, authoring comes R1.5. This is the one piece that reverses a logged BO decision *and* re-opens the **POCDEX write path** — which is currently blocked on the Core team (#31). Keeping it out of R1 keeps the release off that blocker. Flag it explicitly so the reversal is a conscious choice, not a silent scope bomb.

**Agency-admin authentication — open dependency.** Native creation needs an *agency-admin* auth surface, distinct from the officer login (WOG AD) the team is still onboarding (#26, 6-week chain, not yet approved). Who counts as an agency admin, how they authenticate, and whether that auth is even built are all undefined. This is foundational to Epic A and currently absent from the build picture. (→ Pow Hwee / Fabian)

**C@G is the exception — keep it as native as possible.** Careers@Gov stays on its own rails (its own source/integration, not authored through the generic agency creation form). Don't fold C@G into the create flow; it's a distinct path that should feel native to its origin. This is the boundary to hold in Epic A.

**Biggest open questions:** narrow (IJ+Secondment) vs full five-type creation? How does "C@G as native as possible" resolve — read-only ingest, deep integration, or between? Criteria authoring in R1 or R1.5 (recommend R1.5)? Agency-admin auth — does it exist, who owns it? (→ Mark / Jacky / Pow Hwee / Fabian)

### Epic B — Streamlined Application (the apply core)

The end-to-end in-Compass apply flow. Two sides:

- **HR side:** agencies post all job types — including secondments — directly in Compass. New native posting capability (distinct from the MVP interim-form workaround for OTG agencies without a `formsg_url`).
- **Officer side:** a full **in-Compass application form — a native OTEP form**, not an embedded third-party (FormSG / C@G) form. Compass owns the form, pre-filled from the officer's existing OTEP profile (competencies + work history), posting to OTEP's own backend. Officer completes and submits without leaving Compass. No redirects, no embeds.

**Why it's the apply core:** the rest of the apply flow hangs off this. Status tracking needs a submitted application to track. Saved Jobs needs a form to resume. Smart Assistant pre-fills *this* form. (Creation, Epic A, is upstream of all of it — you can't apply to a posting that wasn't created.)

**Form architecture — decided:** native OTEP form, not a FormSG/C@G embed. This was the biggest build-estimate driver and it's now settled. Remaining detail for Pow Hwee: the form's data model and how submissions post to OTEP's backend (feeds Status Tracking, Epic C).

**Cross-squad dependency (flag):** the profile pre-fill (competencies + work history) sits on the competency SSOT owned by Imelda's squad — consumed via an in-code interface, with endpoint specs still in flight between Léo and Kingsley (#18/#41). Both Epic B's pre-fill and Epic E's field-mapping ride on a contract that isn't finalised. Same cross-squad shape that pushed auth to S4+. Don't treat pre-fill as a given.

---

### Epic C — Status Tracking

End-to-end application monitoring, native in OTEP. OTEP owns the state machine: submitted → under review → outcome. **No ATS integration in R1** — that's R2 or whenever a vendor is confirmed.

**Depends on:** Epic B (need a submitted application to have a status).

**Open questions:** what are the states? Who triggers transitions (HR? system?)? Who sees the status — officer only, or HR too? (→ Pow Hwee, needs a data-model pass.)

**Design load (not just a data model):** submitted → under review → **outcome** is a user-facing emotional journey — the "outcome = rejection" state and the "no applications yet" empty state are real design surfaces, not just schema. These are Amber's, and they're currently unnamed. (→ Amber)

---

### Epic D — Saved Jobs

Officers save/bookmark opportunities and resume in-progress applications without losing data.

**Why it pairs with B:** "resume an application" only means something once there's an in-Compass form to half-fill (Epic B). The "save an opportunity" half is lighter and could ship earlier.

**Open questions:** does a save persist across sessions? What happens when a saved posting closes (expiry logic)? (→ Pow Hwee)

---

### Epic E — Smart Assistant

Auto-populates the officer's strengths and experience fields on the application form, drawn from their existing OTEP profile.

**R1 scope is deliberately narrow:** profile-driven pre-fill **only**. NOT CV-upload inference — that's the CIE flow (OTEP-205), a separate capability we are not extending here.

**Depends on:** Epic B (it pre-fills B's form). Effectively an enhancement layer on the application form.

**Design caveat — the pre-fill interaction is load-bearing, even if the *inference* is cut.** Calling E "an enhancement" undersells it. The pre-filled-then-editable form is a known UX trap: what does the officer see when pre-fill is wrong, partial, or stale (the competency-data reconciliation issue, #18)? **Separate the form's pre-fill interaction design (must exist in B regardless) from the smart inference (can flex to Could).** Don't let cutting E leave B's core interaction undesigned.

**Open question:** which profile fields map to which form fields? Needs a field-mapping exercise. (→ Amber / Pow Hwee)

## First-cut priority order (my proposal — the thing to react to)

| # | Epic | Why here | Confidence |
|---|------|----------|------------|
| 1 | **A — Opportunity Creation (narrow: IJ + Secondment)** | The upstream spine and biggest build (2–3x at full scope). Recommend narrow-first: only Internal Jobs + Secondments (no other home post-OTG); full 5-type + criteria authoring = stretch. The capacity driver for the whole release. | High (narrow) / Low (full) |
| 2 | **B — Streamlined Application** | The apply spine. The officer-facing payoff; the native in-Compass form the other apply epics hang off. Scoped in parallel with A, but **built sequentially — FE is the constraint** (see capacity note). | High |
| 3 | **C — Status Tracking** | The other half of "apply inside Compass" — without it officers submit into a black box. New data model = scope early even if it ships after B. | High |
| 4 | **D — Saved Jobs** | High officer value, lower build cost. "Save an opportunity" can ship semi-independently; "resume application" waits on B. Good parallel-track candidate. | Medium |
| 5 | **E — Smart Assistant** | An enhancement on B's form, not a standalone capability. Sequence last; it makes a working form better, it doesn't make the flow work. | Medium |

**The shape:** **two spines, A and B**, are the critical path — creation (agency side) and application (officer side). Different surfaces, so the *scoping* parallelises, but the *build* serialises through one FE. C is scoped alongside B (data model), ships after. D and E are enhancement layers that flex on timing. **If R1 has to be cut: E goes first, then the "resume" half of D. The create-apply-track core (A-narrow + B + C) is non-negotiable** — without it R1 doesn't deliver its promise.

> **The capacity reality to put on the table — FE *and* design.** A alone is a 2–3x scope expansion (net-new agency-admin UI + data model + publish workflow) with **Thomas as sole FE** in a 3-month window. A and B are two net-new surfaces — they are **built sequentially, not in parallel** (one FE). Each also needs a full design pass — forms, validation, error, empty, confirmation, and edit/close lifecycle states — against **Amber, who is shared across squads**. So the constraint is double: serial FE *and* shared design. Honest read: **A+B+C at full breadth likely does not fit.** The realistic R1 is **A-narrow (IJ+Secondment, no criteria authoring) + B + C-minimal**, with everything else flexing. The jam's real job is agreeing that core and the flex — not sequencing all five at full scope.

**Fallback shape (have this ready in the room):** if even A-narrow + B + C doesn't fit, the smallest thing that still delivers is **A-narrow (IJ+Secondment creation) + B (apply) → submission lands, no native status tracking yet (status = email/manual interim, C slips to R1.5).** That still closes the create→apply loop for the orphaned types. Don't walk in without an answer to "what if it doesn't fit?"

## The cut line — MoSCoW (the framework for the jam)

This is the shared vocabulary for the "what's in R1" decision. Bring this as the slide.

| Bucket | Epics | The line |
|--------|-------|----------|
| **Must** | **A-narrow** (IJ + Secondment creation) · B — Application · C — Status Tracking | R1's promise *is* create-apply-track for the orphaned types. Drop any one and R1 doesn't deliver. Non-negotiable. |
| **Should** | D — Saved Jobs ("save an opportunity" half) · **A full 5-type creation** (add STIP/Gig/PSFG) | High value. The full-type stretch lives here — in if capacity allows, first real thing to drop if not. |
| **Could** | E — Smart Assistant (inference) · D's "resume application" half | Enhancements on a working form. First to flex. *(B's pre-fill *interaction* stays in B regardless — only the smart inference is Could.)* |
| **Won't (this release)** | **Ringfencing-criteria authoring** · opportunity recommender · ATS · CIE/CV inference · **SJR creation** | Explicitly out. Criteria authoring re-opens the blocked POCDEX write path (#31) → R1.5. Name them so they don't creep in mid-jam. |

**How to run it in the room:** start by asking Adrian to challenge the **Musts** (if he agrees A-narrow + B + C is the core, the hard part is done). Then negotiate the **Should/Could line** — full-type creation vs narrow is the big one, and that's where capacity actually bites. The **Won'ts** are there to defend the boundary, not to debate — especially criteria authoring, which is the silent scope-and-blocker trap.

**If Adrian pushes on the order within a bucket** (e.g. "why D over E?"), fall back to RICE: D has higher Reach (every browsing officer) and lower Effort than E, so it wins on value-per-build-cost. You don't need to score all five — just the pair he's contesting.
