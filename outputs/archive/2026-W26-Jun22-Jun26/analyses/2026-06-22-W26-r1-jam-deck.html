01 What's broken today The problem
CareerCompass is a read-only job board. An officer can browse and discover — then hits Apply and leaves the platform entirely. Nothing comes back.
Officer journey today
1
Browse Compass — discovers opportunity, reads detail
2
Clicks Apply — redirected to FormSG or C@G external site
3
Fills form from scratch — no profile pre-fill, manual entry
4
Submits externally — Compass has zero record of this
5
Waits. Hears nothing. — no status, no notification, must chase manually
Agency side today
  • Internal Jobs + Secondments are orphaned. No creation tooling exists anywhere. These types were pulled from MVP.
  • Applications arrive via FormSG or email — manual, unstructured.
  • No manager queue. No shortlisting. No status-back mechanism.
  • Status updates = HR chasing candidates individually.
Why this blocks the North Star: 10% of officers completing a development action by Mar 2027 can't be measured if every application happens outside the platform and never comes back. R1 closes this gap.

03 Why R1 now — the OKR case Rationale
🎯

North Star: 10% completion rate by Mar 2027

10% of officers complete a development action originating from CareerCompass. You can't hit this if "apply" still means leaving the platform. MVP establishes the baseline — R1 moves the needle.

👥

OKR 2: 1,850 officers applied via CareerCompass by Q4 2028

The funnel starts at R1. Every sprint it slips is compounded time lost on adoption. FormSG redirects don't count toward this number.

⏱️

Status latency OKR: ≤24 hours from hiring manager action

Needs a native state machine and vendor webhook agreements — both have multi-week lead times. Can't be retrofitted after R2.

🔄

OTG feature parity: 50% of required features built in CareerCompass by Q1 2027

Native opportunity creation (Epic A) is the primary driver. Without it, OTG migration stalls and pilot agencies can't cut over.

04 Ideal R1 user journeys — 3 personas, 3 lanes User experience
👤 Persona 1
Intentional Mover

Senior officer, targeted, time-pressured. Already decided to apply before opening the platform — the apply flow is where you win or lose them.

Epics A + B + C critical

"I don't want to retype everything I already gave HR."

👤 Persona 2
Passive Watcher

Early career, open but not searching. Needs a holding space for opportunities they're considering. Every session starts from zero without saved jobs.

Epic D is the activation feature

"I'll apply when I'm ready — I just don't want to lose it."

🏛️ Persona 3
Posting Manager

Agency HR officer. Manages 5–20 active postings. Tracks everything in email + spreadsheet today. Needs the loop closed in one system.

Epics A + C unlock this persona

"I don't want to chase HR records to assess one applicant."

⚠️ The Seam — still undiscovered

The handoff from officer submission (Lane 1) to posting manager queue (Lane 3) is undesigned. This is where the 24hr latency OKR actually lives — and the highest-risk surface in R1. See next slide.

05 Lane 1 — Officer applies (Intentional Mover) Epics B + C
1

Browse listing + open detail page

Filter by type, search by keyword. Officer already knows what they want (MVP feature).

2

Click Apply → pre-filled form appears in-Compass

Profile fields auto-populate: name, grade, agency, competencies. No redirect. (Epic B)

3

Review, edit, add motivation statement

Corrects stale pre-fill. Adds what's genuinely new. The correction flow needs intentional design.

4

Submit → confirmation + reference number

"Your application has been submitted." Timestamp and reference visible immediately.

5

"My Applications" tab — live status tracking

Submitted → Under Review → Outcome. No more chasing by email. (Epic C)

6

Push notification when status changes

Officer sees the update without logging in to check. "Even a 'no decision yet' is better than silence."

⭐ Aha moment

Officer sees their profile already loaded into the form. "I don't have to retype everything." This is when R1 earns trust and justifies switching from OTG.

⚠️ Risk: stale pre-fill

Pre-fill that's wrong is worse than no pre-fill. Officers who see inaccurate data lose trust faster than they gain it.

⚠️ Leap of faith: channel choice (A1)

Will officers choose CareerCompass over navigating to OTG by habit? MVP apply-CTR data (Oct–Nov 26) validates this. If CTR <10%, investigate before R1 build starts.

06 Lane 2 — Save and return (Passive Watcher) Epic D
This persona isn't disengaged — they're deferring. Without Saved Jobs, every session starts from zero and CareerCompass can't build a habit.
1

Browses listing — not ready to apply

Sporadic session. Sees something interesting but doesn't want to commit right now.

2

Saves the opportunity (Epic D)

Bookmarks it. Closes tab. Cross-session persistence — it's still there when they come back.

3

Leaves, comes back later

"Saved Jobs" tab surfaces it on re-entry. No starting from zero.

4

"Closes in 3 days" nudge

Deadline proximity indicator creates mild urgency. Officer decides to act.

5

Decides to apply → joins Lane 1

Saved job is the entry point into the apply flow (Epic B). The lanes connect.

Why this is the re-login lever

The 9% OTG re-login rate is this persona's symptom. Saved Jobs + filter persistence convert a one-time visitor into a returning user — which is what the re-login metric improvement requires.

Open design questions

  • Cross-session persistence — how long? 90 days? Forever?
  • What happens when a saved posting closes?
  • Does saving trigger a deadline notification?
07 Lane 3 — Posting Manager: create + review Epics A + C
Creation journey (Epic A)
1

Programme cycle opens → "Create Posting"

"Is this instead of OTG?" Must be unambiguous. Dual-posting is the failure mode that kills trust.

2

Fills structured form

Type, title, competencies, duration, closing date. Agency name pre-filled. Per-type templates reduce blank-page friction.

3

⭐ Preview pane — sees the officer view before publishing

"Oh — this is what they see." Control OTG never gave them. This is the aha moment.

4

Publish → immediately live in listing

"Live now, X officers in pilot agencies can see it." No approval lag (confirm if agency policy requires a gate).

Review journey (Epic C)
5

Applications land in dashboard

Structured profile per applicant — not email. Name, grade, agency, competency tags visible without chasing HR systems.

6

Shortlist / update status

Marks: Shortlisted / Not Proceeding / Hold. Optional note for audit trail. Officers auto-notified on each change.

7

Close posting / mark filled

Posting closes, listing shows "closed" state. No more late submissions arriving after deadline.

08 The seam — the biggest undiscovered surface Risk

The officer-apply journey and the posting-manager journey both go quiet at the same point. Nobody owns stages 7 and 10 — routing in, and status back. That's not an oversight; it's because the seam is undecided.

Officer CareerCompass Posting Manager ────────────────────────────────────────────────────────────────────── Clicks Apply └──────► In-Compass form (Epic B) Officer submits │ ════════ THE SEAM ════════ ← nobody owns this yet ▼ Applications dashboard ◄── Manager reviews Manager updates status (Epic C) ◄──── status syncs back ──────────────┘ Officer sees update in "My Applications"

World A — ATS integration

Submission posts to ATS. ATS is the system of record. Status events webhook back to OTEP. Risk: integration depth + vendor agreement lead time (multi-week external clock).

World B — OTEP-native (recommended)

OTEP builds the record store, routing, and state machine. More build but fully owned. The posting-manager journey only exists in World B if OTEP builds this. Otherwise FormSG emails stay in inboxes and nothing changes for the manager.

Epic B

Status Tracking

End-to-end monitoring in OTEP. State machine: Submitted → Under Review → Outcome. No ATS integration in R1.

Officers bookmark opportunities and resume applications. "Save" ships semi-independently. "Resume" waits on Epic B.

Parallel-track candidate

10 Epic A — Opportunity Creation Priority 1
The spine. Flips CareerCompass from read-only into the system of record — and re-opens the door for Internal Jobs + Secondments that have no other home post-OTG.

Recommended scope — narrow, not full

  • Internal Jobs + Secondments only — no other home
  • Structured creation form (per-type fields)
  • Officer-view preview pane (the aha moment)
  • Publish → immediately live in listing
  • Agency-scoped auth — manager posts for own agency
  • Edit / unpublish an existing posting

Narrow = ~half the build vs full 5-type. This is the main capacity lever.

Scope flags for the jam

  • Full 5-type creation = Should, not Must
  • Criteria authoring: OUT — re-opens POCDEX write path (#31)
  • SJR creation: NOT in R1 unless Mark pulls it in
  • C@G stays on its own rails — not this form

⚠️ Open dependency — agency-admin auth

Who can post? How do they authenticate? Currently zero discovery. Pow Hwee + Fabian need to weigh in before Epic A can be fully scoped.

11 Epic B — Streamlined Application + Smart Pre-fill Priority 2

Apply core

Full in-Compass form — native OTEP, not FormSG. Compass owns the form, posts to OTEP backend. Officer submits without leaving. No redirects.

Smart pre-fill (bundled sub-feature)

Auto-populates strengths and experience from the officer's OTEP profile. Profile-driven only — not CV/CIE inference (OTEP-205, separate capability).

Design note

What does the officer see when pre-fill is wrong, partial, or stale? That interaction needs design regardless of how much "smart" inference we add.

⚠️ Cross-squad dependency (#18 / #41)

Profile pre-fill rides on the competency SSOT owned by Imelda's squad. Endpoint specs between Léo and Kingsley still in flight. Pre-fill is not a given until that contract is finalised.

🔴 P0 open question — for the jam

"Application within CareerCompass" — does it mean absolutely no redirects, or that the experience starts in Compass? This changes R1 engineering load by an order of magnitude.

12 Epic C — Status Tracking Priority 3
Closes the "submit into a black box" problem. Scope the data model early even if it ships after Epic B.

What it delivers

  • OTEP owns the state machine: Submitted → Under Review → Outcome
  • Officer sees live status in "My Applications" tab
  • Push notification when status changes
  • Posting Manager updates status; officers auto-notified
  • No ATS integration — OTEP-native state machine only for R1

Design surfaces to define now

  • "Outcome = rejection" state
  • "No applications yet" empty state
  • Who triggers status transitions — manager manually or ATS event?
  • Who sees the status — officer only, or HR dashboard too?
  • Notification mechanism (none in MVP — needs its own design)
The 24-hr latency OKR lives in the status-back-to-officer path, not in the apply flow. Teams over-invest in visible apply UX and under-invest here.
13 Epic D — Saved Jobs Priority 4
High officer value, lower build cost. The "save" half ships semi-independently as a parallel track to C.
Must have

Save an opportunity

Bookmark any opportunity. Find it later in a "Saved Jobs" tab. Cross-session persistence required.

Ships semi-independently — can run in parallel with C. Lower risk.

  • What happens when a saved posting closes?
  • "Closes in 3 days" deadline nudge
First to cut

Resume an in-progress application

Save draft mid-form, pick up later. Depends on Epic B. Only build if MVP abandonment data shows >40% drop-off mid-form (data available Oct 2026).

Why this matters

The 9% OTG re-login rate reflects Passive Watcher officers who browse once and don't return. Saved Jobs is the activation feature — without it, re-login improvement is structurally blocked.
