HR journey · Internal Jobs (AS-IS vs. TO-BE)

Maintaining Internal Jobs data, before and after

This is a data-architecture story more than a process story. HR still creates and maintains Job IDs and competency data the same way in both states, in Cumulus and HRPS — what changes is that Compass starts pulling a periodic read from HRPS to power discovery. Source: Internal Jobs architecture diagram and the Mobility Programmes comparison artifact.

Read this differently from the IJR/SJR maps: those two lanes are two live paths running at the same time (structured vs. officer-initiated). Here, the two lanes are sequential states of the same system: AS-IS is what's true today, TO-BE is the target architecture. HR doesn't choose a lane, the system moves from one to the other, on a timeline that isn't set yet.

R1 scope boundary: R1 commits to Internal Jobs discovery surfacing in Compass, gated on an undelivered HRPS API with no date yet (R-07, 🔴 Red). Job ID creation and maintenance stay in Cumulus/HRPS in both states — HR's process doesn't change. The open question is whether HRPS's API response supplies ringfencing data directly, or whether Compass has to build that logic itself.

What actually gets better

Officers get one place to discover Internal Jobs instead of two. HR's own maintenance work in Cumulus and HRPS doesn't change, and apply routes cleanly to whichever system hosts the posting.

What HR should not assume is solved

  • Job ID creation and data maintenance still happen entirely in Cumulus/HRPS — Compass doesn't take that over
  • POCDEX is gone, so there's no fallback if the HRPS pull breaks
  • Whether HRPS supplies ringfencing data directly, or Compass has to build it, is unresolved
  • No delivery date yet for the HRPS API access this discovery flow depends on (R-07)

Compass doesn't become a data hub here. Cumulus pushes postings into HRPS one-way, Compass pulls from HRPS only on a periodic sync, and never maintains or holds the data itself. Job ID creation and maintenance stay exactly where they are today, entirely in Cumulus and HRPS.

POCDEX going away is a real risk, not just cleanup. Today, if the one-way HRPS-to-Cumulus sync fails, POCDEX still aggregates both systems' Job ID data, so Compass has a fallback path to read from. In TO-BE, POCDEX is retired. If the periodic HRPS→Compass pull breaks, there's no fallback left — that's the exact risk named in the Mobility Programmes comparison artifact's footnotes.

Don't oversell TO-BE as resolved. Apply as a redirect to the hosting system is a confirmed architecture decision, not TBC. What's still open is narrower: whether HRPS's API response supplies ringfencing data directly, or whether Compass has to build that logic itself (R-07).
