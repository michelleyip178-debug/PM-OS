R-07 HRPS API access for Internal Jobs — architecture corrected 23 Sep, still no delivery date Integration Corrected 23 Sep ▸
Category
Integration — escalated 23 Sep as a named critical dependency in Adrian's R1 scope slide; architecture corrected 23 Sep, same day, by Michelle — the source diagram used to build the Internal Jobs journey maps was misread
Risk
Mainstream/Internal Jobs discovery depends on confirmed HRPS API access. 21 Sep findings: HRPS has no obvious API currently identified but the team believes one could be built; internal-job flagging exists and is confirmed identifiable. 23 Sep architecture correction — supersedes the "Compass reads from both HRPS and Cumulus" framing used in the journey maps and comparison artifacts: Cumulus pushes postings into HRPS's Internal Job Portal (one-way, system-to-system — Compass has no direct relationship with Cumulus at all). Compass pulls from HRPS only, at regular sync intervals, not via a live two-way API — maintenance of postings stays entirely in the HR systems, Compass does not "hold" or maintain the data itself, it's a periodic read. Apply is confirmed as a redirect, not TBC — officers link out to whichever system actually hosts the posting (HRPS or Cumulus), since HRPS's record to Compass carries the original hosting system's link even though Compass itself never talks to Cumulus directly. Still open, newly sharpened: whether HRPS supplies ringfencing criteria directly, or Compass has to build ringfencing logic itself — this is now the single open technical question, replacing the previous "does the API exist at all" framing now that the pull-based, HRPS-only, redirect-apply architecture is confirmed. POCDEX's retirement in the target state is unaffected by this correction.
Impact
Internal Job Market support depends on this ringfencing-source question resolving — if HRPS doesn't supply it, Compass has to build agency-ringfencing logic from scratch, which is a different and larger engineering ask than consuming a ready-made field.
Mitigation
Get a direct answer from HRPS: does the API response include ringfencing/agency-tagging data, or does Compass need to derive/build it. Pure ingestion fallback via C@G (F-23, confirmed locked) remains the fallback if HRPS access doesn't resolve at all.

R-25 IJR follows the STIPs & Gigs model end to end — resolved, ready for Epic D Scope Resolved 24 Sep ▸
Category
Scope — resolved 24 Sep, closing the creation-model question that blocked Epic D
Risk
IJR is confirmed R1 scope, fully mirroring STIPs & Gigs' shape. Self-serve creation (any officer posts, no HR gate), native discovery, structured-form apply, in-app applicant review for Agency HR, and officer status tracking, all inside Compass, same as Epic A. The one remaining difference from STIPs & Gigs: what happens after a decision is made stays offline — Agency HR's actual matching/assignment logic (if IJR still involves pooling multiple applicants against multiple roles) is not being rebuilt as a Compass feature; Compass provides the review/decide interface, not an algorithmic matching engine. Impact
Epic D can now be drafted as real, groomable stories, directly adapting Epic A's story shapes (Creation, Publish & Lifecycle, Application, Notification & Review, Decision) rather than waiting on a creation-model answer. One nuance to watch: if IJR's traditional "matching exercise" assumed multiple applicants get compared against multiple roles simultaneously (not a 1:1 Offer/Reject like STIPs & Gigs), the Decision-stage story may need to diverge from Epic A's shape even though Creation/Application/Review can copy directly.
Mitigation
Draft Epic D's stories directly off Epic A's structure (US-A1 through US-A13 equivalents). Confirm one remaining nuance with Adrian: does IJR's "Decision" stage stay a simple per-applicant Offer/Reject like STIPs & Gigs, or does it need to preserve the traditional pooled-matching shape (multiple applicants weighed against multiple roles at once) — this is the one place "same as STIPs & Gigs" might not fully apply.
