## What's broken today

CareerCompass is a read-only job board. An officer can browse and discover — then hits Apply and leaves the platform entirely. Nothing comes back.

**Officer journey today:**
1. Browses Compass, finds an opportunity
2. Clicks Apply — redirected to FormSG or C@G external site
3. Fills the form from scratch (no profile pre-fill, manual entry)
4. Submits externally — Compass has zero record of this
5. Waits. Hears nothing. Has to chase manually for any status update.

**Agency side today:**
- Internal Jobs + Secondments are orphaned. No creation tooling exists anywhere — these types were pulled from MVP.
- Applications arrive via FormSG or email — manual, unstructured.
- No manager queue. No shortlisting. No status-back mechanism.
- HR chases candidates individually for every update.

**Why this blocks the North Star:** The OKR is 10% of officers completing a development action by Mar 2027. You can't measure completion if the action happens outside the platform and nothing comes back. Every application is invisible to Compass the moment the officer clicks Apply.

---

## R1 in one line

MVP gets an officer to the *door* of an opportunity — browse, filter, view, click out to apply. **R1 brings both ends in-house:** agencies create opportunities directly in CareerCompass, officers apply without leaving it. Create it, post it, pre-fill it, submit it, track it, save it. CareerCompass stops being a read-only window onto OTG and becomes the system of record.

---

## Why R1 now — the OKR case

Three OKR targets only unlock if R1 ships on time (Q1 2027):

- **North Star:** 10% of officers complete a development action by Mar 2027. You can't hit this if "apply" still means leaving the platform and following up manually.
- **OKR 2:** 1,850 officers applied via CareerCompass by Q4 2028. The funnel starts at R1 — every sprint it slips is compounded time lost on adoption.
- **Status latency:** Application status updates ≤24 hours of hiring-manager action. This needs a native state machine — can't be retrofitted after R2.
- **OTG parity:** 50% of required features built in CareerCompass by Q1 2027. Native creation (Epic A) is the primary driver.

The R1 epics (A–D) map directly to these. Without A+B, there's no application in-Compass. Without C, the status latency OKR has nothing to measure. D (Saved Jobs) is the retention layer that keeps officers coming back.

## The ideal R1 user journeys

Three lanes, three personas. Each maps to a different part of the R1 build.

**Lane 1 — Intentional Mover (Epics B + C):**
Senior officer, targeted, time-pressured. Browses → finds opportunity → clicks Apply → pre-filled form appears in-Compass → reviews, edits, adds motivation statement → submits → confirmation + reference number → "My Applications" tab shows live status → push notification when status changes.

*Aha moment:* profile already loaded into the form. "I don't have to retype everything."
*Risk:* stale pre-fill erodes trust faster than no pre-fill.

**Lane 2 — Passive Watcher (Epic D):**
Early career, open but not searching. Browses → saves an opportunity → closes tab → returns later → "Saved Jobs" tab surfaces it → "Closes in 3 days" nudge → decides to apply → joins Lane 1.

*Why it matters:* the 9% OTG re-login rate is this persona's symptom. Saved Jobs converts a one-time visitor into a returning user.

**Lane 3 — Posting Manager (Epics A + C):**
Agency HR. Manages 5–20 active postings. Creates posting in OTEP native form → sees officer preview pane (aha moment: "this is what they see") → publishes → applications land in a structured dashboard → shortlists / updates status → officers auto-notified → closes posting.

*Unlock condition:* this persona's dashboard only exists if we build the record store and state machine in OTEP (World B). If we go World A with an external ATS, the manager journey doesn't exist in R1.

**The seam — the biggest undiscovered surface:**

Both the officer journey (Lane 1) and the posting manager journey (Lane 3) go quiet at the same point. The officer-submits → submission-routes-to-manager-queue → status-back-to-officer chain is undesigned. This is where the 24hr latency OKR actually lives.

Two possible worlds:
- **World A (ATS):** submission posts to an ATS; ATS is system of record; status webhooks back to OTEP. Risk: integration depth + vendor agreement lead times (multi-week external clock).
- **World B (OTEP-native, recommended for R1):** OTEP builds the record store, routing, and state machine. More build, fully owned. The only path where the posting-manager persona exists in R1.

**This is the ATS fork decision (C1) — the gate for everything downstream. Don't leave the jam without a direction.**

## The 4 epics

### Epic A — Opportunity Creation
Agencies author and manage postings directly in CareerCompass: a structured creation form, the posting lives in OTEP's DB, validation + publish workflow, and the edit/close lifecycle.

**Recommended scope — narrow, not full:**
Lead with **Internal Jobs + Secondments only**. These are the two types with no other home post-OTG (pulled from MVP because there's no creation tooling). Full 5-type creation (adding STIP, Gig, PSFG) is the stretch, not the base.

**Why this is the spine:** it flips CareerCompass from read-only into the system of record. It's also the prerequisite that lets Internal Jobs + Secondments back in.

**Scope flags for the jam:**
- Narrow (IJ+Secondment) = ~half the build vs full 5-type. This is the capacity lever.
- **Criteria authoring: recommend OUT of R1.** Keeps R1 off the blocked POCDEX write path (#31). Criteria stays OTG-read for R1; authoring comes R1.5.
- **SJR: NOT in R1 creation** unless Mark explicitly pulls it in.
- **C@G: stays on its own rails**, not the generic create form.
- Agency-admin auth is an **open dependency** — who they are and how they authenticate is currently undefined. (→ Pow Hwee / Fabian)

---

### Epic B — Streamlined Application + Smart Pre-fill
Two things bundled together: the native in-Compass apply form, and intelligent pre-population from the officer's profile.

**Apply core:**
A full in-Compass application form — native OTEP form, not a FormSG/C@G embed. Compass owns the form, pre-filled from the officer's OTEP profile (competencies + work history), posting to OTEP's own backend. Officer completes and submits without leaving Compass. No redirects.

**Smart pre-fill (folded in from original Epic E):**
Auto-populates the officer's strengths and experience fields on the form, drawn from their existing OTEP profile. This is **profile-driven pre-fill only** — not CV-upload inference (that's OTEP-205, a separate capability). The pre-fill is a sub-feature of the form, not a standalone epic.

**Design note:** The pre-filled-then-editable form needs intentional design even if the smart inference is cut. What does the officer see when pre-fill is wrong, partial, or stale? That interaction lives in B regardless of how much "smart" we add. Don't let the inference question leave the core form interaction undesigned.

**Cross-squad dependency (flag):**
Profile pre-fill rides on the competency SSOT owned by Imelda's squad — endpoint specs still in flight between Léo and Kingsley (#18/#41). Pre-fill is not a given until that contract is finalised.

---

### Epic C — Status Tracking
End-to-end application monitoring, native in OTEP. OTEP owns the state machine: submitted → under review → outcome. **No ATS integration in R1** — that's R2 or whenever a vendor is confirmed.

**Depends on:** Epic B (need a submitted application to have a status).

**Design surfaces to define now:** The "outcome = rejection" state and "no applications yet" empty state are real design surfaces, not just schema. Who triggers transitions? Who sees the status — officer only, or HR dashboard too? (→ Amber + Pow Hwee)

**Note:** The 24hr latency OKR lives in the status-back-to-officer path, not in the apply flow. Teams over-invest in the visible apply UX and under-invest here.

---

### Epic D — Saved Jobs
Officers save/bookmark opportunities and resume in-progress applications without losing data.

**Two halves:**
- "Save an opportunity" — lighter, can ship semi-independently
- "Resume an application" — waits on Epic B (needs a form to resume). Only build if MVP abandonment data shows >40% drop-off mid-form (data available Oct 2026).

**Open questions:** cross-session persistence (how long — 90 days? forever?), what happens when a saved posting closes, does saving trigger a deadline notification? (→ Pow Hwee)

## Priority order

| # | Epic | Why here | Confidence |
|---|------|----------|------------|
| 1 | **A — Opportunity Creation (narrow: IJ + Secondment)** | Upstream spine. Biggest build at full scope — narrow-first halves the risk. IJ+Secondment have no other home. | High (narrow) / Low (full) |
| 2 | **B — Streamlined Application + Smart Pre-fill** | Officer-facing payoff. The native form everything else hangs off. Smart pre-fill folded in as sub-feature — don't treat it as a separate epic. | High |
| 3 | **C — Status Tracking** | Closes the "submit into a black box" problem. New data model = scope early even if it ships after B. | High |
| 4 | **D — Saved Jobs** | High officer value, lower build cost. "Save an opportunity" can ship semi-independently as a parallel track. | Medium |

**The critical path:** A and B are the two spines (creation + application). Different surfaces — scoping parallelises, but **build serialises through one FE (Thomas)**. C is scoped alongside B, ships after. D is the parallel-track candidate.

**If R1 has to cut:** D's "resume application" half goes first, then D entirely. A-narrow + B + C is the non-negotiable core — without all three, R1 doesn't close the create→apply→track loop.

**Fallback shape (have this ready):** if A-narrow + B + C doesn't fit, the minimum is **A-narrow + B, with C as email/manual interim (slips to R1.5).** Still closes the loop for the orphaned types.
