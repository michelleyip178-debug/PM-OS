# GovTech Singapore Low-Risk Cloud System Security Plan (SSP) Checklist & Reference Manual
*Version 1.0 (Optimized Reference Standard for Low-Risk Cloud Systems)*

> **Saved to PM-OS 2026-09-03.** Third file in the govtech compliance reference set — companions: `govtech-ict-rmm-methodology.md` (the 6-stage risk process) and `govtech-ict-rmm-risk-library.md` (baseline risk register). This one is the **security control baseline** for the SSP, used alongside the risk assessment for Career Compass pre-go-live readiness. Career Compass profile: **Low-Risk Cloud System** on GCC, Intranet-facing, entity data, WOG AD auth, integrates POCDEX / CSC / Jumpstart.

This reference manual compiles the complete security control baseline for **Low-Risk Cloud Systems** under GovTech Singapore's IM8 (Instruction Manual 8) and Government on Commercial Cloud (GCC) frameworks.

It is designed to serve as a structured knowledge reference for **Claude** (and other AI engines) to automate SSP preparation, conduct gap analyses on existing system architectures, review implementation statuses, and verify regulatory alignment.

---

## 1. System Prompt & Integration Instructions for Claude
When analyzing a system architecture or auditing an SSP using this document, adopt the following behavior:

1.  **Understand the Target Environment:** This checklist applies specifically to **Low-Risk Cloud Systems** hosted on commercial cloud infrastructures (such as GCC).
2.  **Audit Implementation Status:** For each control, review the user's implementation details. Check if they have met the **Statement** and followed the **Recommendations**.
3.  **Validate Risk/Rationale:** If a control is not implemented or is "Not Applicable," verify that the agency's justification covers the specific threat identified in the **Risk/Rationale** column.
4.  **Reference Mapping:** Ensure all security implementations align with the standard references provided (e.g., MVSP, IM8 Cloud Security, NIST SP 800-53, or Singapore Government Developer Portal standards).
5.  **Identify Profile Levels:** Use the **Profile Level (0, 1, 2)** to identify the criticality of the control.
    *   **Level 0:** Mandatory base governance.
    *   **Level 1:** Standard baseline controls for all systems.
    *   **Level 2:** Enhanced controls for slightly higher sensitivity/complexity.

### 2.1 Application Security (as)
These controls govern application-level development, session handling, user inputs, and logical application boundaries.

| ID | Title | Security Statement | Recommended Implementations & Actions | Risk / Rationale | Profile Level | References |
| :--- | :--- | :--- | :--- | :--- | :---: | :--- |
| **as-1** | Input Validation | Validate all application inputs to ensure that they match the expected type, structure, or format. | Strictly validating inputs against a comprehensive schema prevents injection attacks caused by inserting special characters or content that would cause the application to perform incorrect operations. | Without input validation, there's a heightened risk of injection attacks, data manipulation, or system crashes due to unexpected input, potentially leading to unauthorised access or disruption of services. | 1 | MVSP 2.5: Security libraries; IM8 Cloud Security (IaaS and PaaS): 1.7/S1c, 1.7/S8b; IM8 On-Premise ADS (Non-S): 1.1/S1b |
| **as-2** | Parameterised Interfaces | Use parameterised interfaces for database queries or system commands. | Parameterised interfaces such as Object-Relational Mapping (ORM) libraries ensure that parameters used in database queries or system commands are properly sanitised and prevent injection attacks. | Failure to use parameterised interfaces increases the vulnerability to SQL injection or command injection attacks, posing a significant risk of unauthorised access, data manipulation, or even potential system compromise. | 1 | MVSP 2.5: Security libraries; IM8 Cloud Security (IaaS and PaaS): 1.7/S8c; IM8 On-Premise ADS (Non-S): 1.1/S1c; IM8 Data Protection (Data Security): 1.7, 1.7/S1, 1.7/S2, 1.7/G1 |
| **as-3** | Output Sanitisation | Sanitise all application outputs that will be used to render an HTML document. | Any application outputs that are returned to the requester and used to render an HTML document can lead to cross-site scripting (XSS) attacks if they contain special characters that change the rendering of the HTML document by the browser. | Lack of sanitisation for application outputs used in rendering HTML documents exposes the system to the risk of cross-site scripting (XSS) attacks, allowing malicious code execution in browsers. | 1 | MVSP 2.5: Security libraries; IM8 Cloud Security (IaaS and PaaS): 1.7/S8e; IM8 On-Premise ADS (Non-S): 1.1/S1e,k,l |
| **as-4** | Authentication Mechanism Rate-Limiting | Apply rate-limiting on all authentication mechanisms to deter brute-force attacks. | Consider rate-limiting to a maximum of 3 consecutive failed authentication attempts within 15 minutes or other reasonable rate limits. Time delays between log-on attempts reduce the risk of successful brute-forcing attacks. Bot mitigation tools such as CAPTCHA can further reduce this risk. | Without rate-limiting, there's an increased risk of unauthorised access as attackers may exploit weak credentials through repeated login attempts. | 1 | MVSP 2.4: Password policy; IM8 Cloud ADS: 2.2/S1j, 2.2/S5b; IM8 On-Premise ADS (Non-S): 2.2/S5 |
| **as-5** | Password Requirements | Where SSO or passwordless is not supported, verify that passwords are at least 12 characters in length and include a number or special character. | Latest NIST SP 800-63B guidelines found that password length is a primary factor in determining the strength of a password while composition and complexity rules provide marginal security benefits. | Short or commonly used passwords increase the vulnerability to unauthorised access, potentially leading to compromised accounts and unauthorised activities on the system. | 1 | MVSP 2.4: Password policy; NIST SP 800-53 IA-5(1): Password-based Authentication; IM8 Cloud Security (IaaS and PaaS): 1.4/S1a, 1.4/S2a; IM8 On-Premise ADS (Non-S): 2.2/S1 |
| **as-6** | Password Salting and Hashing | Store passwords as salted hashes using a password hashing scheme that is resistant to offline attacks such as those described in NIST SP 800-63b. The salt should be: (1) Cryptographically secure pseudo-random; (2) At least 32 bits long; (3) Randomly generated per account. | Refer to NIST SP 800-90Ar1 for suitable pseudo-random number generators. Refer to NIST SP 800-63b Memorized Secret Verifiers section for suitable hashing schemes, including Argon2, scrypt, and PBKDF2. For application source code, use secure functions (e.g., `crypto.randomBytes` in Node.js, `java.security.SecureRandom.nextBytes` in Java). | Without salting and hashing, in case of a data breach, exposed passwords can be easily extracted, leading to potential compromise of accounts and sensitive information. | 1 | MVSP 2.4: Password policy; IM8 Cloud Security (IaaS and PaaS): 1.4/S3; IM8 On-Premise ADS (Non-S): 2.2/S3 |
| **as-7** | Access Control Check Enforcement | Perform access control checks on all authenticated requests. | Utilise authorisation filters or middleware to force all authenticated requests to undergo access control checks. | Failure to perform access control checks on authenticated requests increases the risk of unauthorised access to sensitive data or functionalities, potentially leading to data breaches and misuse of system resources. | 1 | MVSP 3.3: Vulnerability prevention; IM8 Cloud Security (IaaS and PaaS): 1.7/S8a |
| **as-8** | Secrets Management | Securely store secrets in an appropriate secrets management solution with access control enforcement, encryption, and monitoring. | Secrets include API keys, access keys, and other static credentials. Do not store secrets unencrypted in source code or configuration files. Store secrets in cloud-native solutions like AWS Secrets Manager and Azure Key Vault or cloud-agnostic solutions like HashiCorp Vault. Use GitHub Actions secrets instead of variables. | Exposure of sensitive information and unauthorised access to system credentials may occur if application secrets are stored insecurely or hard-coded in source code. | 1 | IM8 Cloud Security (IaaS and PaaS): 1.7/S11; IM8 On-Premise ADS (Non-S): 1.1/S1f, 2.2/S4, 3.1/S1, 3.1/S4; IA-5(7): No Embedded Unencrypted Static Authenticators; IA-5(6): Protection Of Authenticators; IM8 Cloud Security (IaaS and PaaS): 1.4/S24; IM8 Data Protection (Data Security): 1.21 |
| **as-9** | Content Security Policy (CSP) | Set minimally permissive CSP response headers to mitigate cross-site scripting attacks. | Utilise the relevant fetch directives such as `default-src`, `script-src`, `style-src`, `connect-src`, `img-src`, `media-src` and `object-src` to prevent loading of scripts from malicious sources. Refer to OWASP Secure Headers Project Best Practices. | Without minimally permissive Content Security Policy (CSP) headers, the risk of cross-site scripting attacks, leading to unauthorised script execution and potential data theft, is increased. | 1 | MVSP 2.3: Security Headers; IM8 Cloud Security (IaaS and PaaS): 1.7/G7 |
| **as-10** | HTTP Strict Transport Security (HSTS) | Set HTTP Strict Transport Security (HSTS) response headers with a maximum age value of at least 1 year (31536000 seconds) to mitigate protocol downgrade attacks. | Refer to the OWASP Secure Headers Project Best Practices for recommended header values. | Failure to implement HTTP Strict Transport Security (HSTS) with a sufficient maximum age may expose the system to protocol downgrade attacks, compromising the security of communication channels. | 2 | IM8 Cloud Security (IaaS and PaaS): 1.7/G4 |
| **as-11** | Session Management | Require users to re-authenticate after their session exceeds 720 hour(s) or terminate the session. | NIST SP 800-63B recommends re-authentication once per 30 days for AAL1, 12 hours or 30 mins inactivity for AAL2, and 12 hours or 15 mins inactivity for AAL3. Re-authenticate when roles, credentials, or privileged actions change. | Not re-authenticating regularly and at suitable checkpoints could allow someone who has access to the account to carry out unauthorised actions. | 1 | NIST SP 800-53 AC-12: Session Termination; NIST SP 800-53 IA-11: Re-authentication; IM8 Cloud ADS: 2.5/S2; NIST SP 800-63B 4.2.3: Reauthentication; IM8 On-Premise ADS (Non-S): 2.5/S2 |
| **as-12** | Malware Scanning of Uploaded Files | Scan file uploads for malware before further processing by the system. | Consider uploading the files to temporary storage for malware scanning on ephemeral compute like serverless functions before moving safe files to another storage for further processing or unsafe files to quarantine storage. | Without scanning uploaded files for malware, there's an increased risk of exploits or infection for consumers of the files. | 2 | NIST SP 800-53 SI-3: Malicious Code Protection |
| **as-13** | Exposure of Internal System Details | Prevent the unnecessary disclosure of internal system details to Public Users. | Ensure all system messages and notifications are informative yet secure. These messages should be contextually appropriate, providing relevant information without exposing internal system details such as debug information, stack traces, or software versioning. | Disclosure of internal system details or debug stack traces can expose vulnerabilities, software versions, and system architecture, potentially leading to targeted attacks, exploitation of known vulnerabilities, and unauthorised access to sensitive systems or data. | 2 | None |
| **as-14** | Secure Cryptographic Libraries | Use reputable and secure cryptographic libraries and functions to handle cryptographic operations. | Follow the OWASP Cryptographic Storage Cheat Sheet for best practices in securely implementing cryptographic operations. Regularly update libraries and prefer widely recognised ones such as OpenSSL. Consider using libraries that are FIPS 140-2 or FIPS 140-3 compliant for enhanced security assurance. | Using insecure cryptographic libraries and functions can expose applications to significant security risks, such as data breaches and unauthorised access, compromising sensitive information. | 2 | OWASP Cryptographic Storage Cheat Sheet; NIST CMVP Validated Modules |
| **as-15** | Password Change | Enforce password change upon suspected account compromise. | Implement mechanisms to detect signs of account compromise, such as unusual login activity or multiple failed login attempts. Notify users promptly to change their passwords and provide guidance on creating strong, unique passwords. Consider integrating multi-factor authentication to enhance security. | Failure to enforce password changes upon suspected account compromise increases the risk of prolonged unauthorised access, leading to potential data breaches and exploitation of systems. | 1 | None |

### 2.2 Software Development & Supply Chain (sc)
These controls focus on secure source code repositories, code validation, release automation, and managing transitive third-party libraries.

| ID | Title | Security Statement | Recommended Implementations & Actions | Risk / Rationale | Profile Level | References |
| :--- | :--- | :--- | :--- | :--- | :---: | :--- |
| **sc-1** | Code Repository | Manage the codebase in a central code repository with version control. | Use common internal platforms that provide Git repository services. | Absence of centralised code repository and version control increases the risk of code inconsistencies, loss of code history, and difficulties in collaboration, potentially leading to errors and security vulnerabilities. | 1 | IM8 Cloud ADS: 7.1/S1; IM8 On-Premise ADS (Non-S): 6.1/S1 |
| **sc-2** | Commit Signing | Configure the code repository to reject unsigned commits. | Use GitLab's push rules, GitHub's branch protection rules or similar code repository controls to reject unsigned commits on push. | Allowing unsigned commits in the code repository introduces the risk of unauthorised or malicious code changes, compromising the integrity and security of the software development process. | 2 | None |
| **sc-3** | Peer Review | Require peer review and approval by a designated reviewer before merging into the default branch. | Use GitLab's protected branch and merge request settings, GitHub's branch protection settings or similar code repository controls to enforce this. | Without peer review and approval before merging, there is an increased risk of introducing undetected coding errors, security vulnerabilities, and maintaining codebase consistency may become challenging. | 1 | IM8 Cloud Security (IaaS and PaaS): 1.1/S2; IM8 Cloud ADS: 8.1/G1; IM8 On-Premise ADS (Non-S): 8.1/G1 |
| **sc-4** | Dependency Manifest Version Pinning | Pin direct and transitive dependency versions in the application's dependency manifest. | Dependency manifests such as `package-lock.json` for npm and `Pipfile.lock` for pipenv allow you to pin dependency versions. | Failure to pin direct and transitive dependency versions in the application's manifest may lead to version drift, introducing compatibility issues, security vulnerabilities, and unpredictability in the software environment. | 1 | SLSA Build L1: Provenance exists; IM8 Cloud ADS: 8.1/G4; IM8 On-Premise ADS (Non-S): 8.1/G4 |
| **sc-5** | Build and Release Process | Use a consistent build and release process that generates a record of how the release artefact was built and deployed. | Consider automated build and deploy tools such as CI/CD Pipelines, Infrastructure as Code (IaC) and other scripts, which allow for signing and validation of build artefacts. If automation is not possible, develop and implement release management processes. | Inconsistent and unmanaged releases may lead to configuration drift, increased likelihood of errors, and unapproved changes to releases. | 1 | MVSP 3.5: Build and release process; SLSA Build L1: Provenance exists; IM8 Cloud Security (IaaS and PaaS): 1.7/S22; IM8 Cloud ADS: 6.1/G4 |
| **sc-6** | Dependency Installation during Deployment | Only install pinned versions in the manifest when installing dependencies during deployment. | Use package manager commands such as `npm ci` for npm and `pipenv sync` for pipenv that ensure only versions specified in the manifest are installed rather than the latest version. | Failure to install only pinned versions of dependencies during deployment increases the risk of introducing unforeseen changes, compatibility issues, and potential security vulnerabilities into the deployed environment. | 1 | SLSA Build L1: Provenance exists |
| **sc-7** | Software Artefact Signing | Sign software artefacts such as code and container images using a trusted source during build. | Use tools or services like Cosign or AWS Signer to sign and verify code. | Unsigned code and container images pose a risk of tampering, impersonation, and the injection of malicious code during the build process, compromising the integrity and security of the deployed software. | 2 | SLSA Build L2: Hosted build platform; IM8 Cloud ADS: 1.7/G9, 8.1/G1 |
| **sc-8** | Software Artefact Signature Verification | Verify the signatures of code and artefacts before deployment or runtime. | Implement a signature verification step such as a pipeline stage or Kubernetes Admission Controller. | Without verifying the signatures of code and artefacts before deployment or runtime, there's an increased risk of deploying tampered or malicious software, compromising the integrity and security of the system. | 2 | SLSA Build L2: Hosted build platform; IM8 Cloud ADS: 1.7/G9; IM8 Cloud Security (IaaS and PaaS): 1.7/S20; IM8 Cloud ADS: 8.1/G12 |
| **sc-9** | Internal Code Collaboration and Sharing | Share source code internally to enhance code quality, accelerate innovation, and improve problem-solving efficiency. | Adopt InnerSource practices for internal collaboration, utilising Git platforms to manage and share code repositories internally. Source code should be evaluated for suitability for InnerSourcing (e.g. check for confidential algorithms or embedded sensitive data). Follow the Singapore Government Developer Portal framework. | Restricting code repositories to closed source can result in duplicated efforts, hinder collaborative learning, and lead to missed bugs or vulnerabilities. | 2 | Singapore Government Developer Portal - Innersource in the Government |

### 2.4 Network Security (ns)
These controls dictate logical separation, edge security, inter-service encryption, and boundary protection.

| ID | Title | Security Statement | Recommended Implementations & Actions | Risk / Rationale | Profile Level | References |
| :--- | :--- | :--- | :--- | :--- | :---: | :--- |
| **ns-1** | Network and System Component Segmentation | Segment and isolate system components into separate physical and logical networks or environments based on their security requirements and risk levels. | Deploy firewalls, security groups, and API gateways. In cloud environments, implement tiered network architecture: public-facing in public subnets, backend in private subnets with controlled egress. Use micro-segmentation. | Failure to segregate private and public resources within distinct subnets in a virtual network increases the risk of unauthorised access to sensitive data, as private resources may be exposed to the public internet. | 1 | IM8 Cloud Security (IaaS and PaaS): 1.5/S1, 1.5/S2, 1.7/S14, 1.5/S6b; IM8 On-Premise IS (Non-S): 4.2/S1a; IM8 On-Premise AAS (Non-S): 1.1/S1, 2.1/S1 |
| **ns-2** | Access Restrictions on CSP Resources Outside Virtual Network | Restrict access to CSP resources outside of a virtual network (e.g., Lambda, DynamoDb, S3, CloudFront) using access controls or application layer authorisation. | Apply access restrictions appropriate to the resource type: Restrict DynamoDB and S3 with IAM policies and block public S3 access. Restrict API Gateway with Lambda authorisers or application-layer middleware. If exposed to private subnets, create a private API. | Lack of access restrictions raises the risk of unauthorised access, data exposure, and potential misuse of critical services, compromising the overall security posture. | 1 | IM8 Cloud Security (IaaS and PaaS): 1.5/S2, 1.5/S5, 1.7/S23 |
| **ns-3** | Deny by Default - Allow by Exception | Deny network communications traffic by default and allow network communications traffic by exception at managed interfaces. | Configure network ACLs and security groups to deny all traffic by default. Only allow traffic to/from specific hosts and ports by exception. For egress traffic, consider whitelisting domains at the application layer or DNS resolver. | Without network access controls, there's an increased risk of unauthorised or malicious network access, leading to potential security breaches and compromise of system integrity. | 1 | NIST SP 800-53 SC-7(5): Deny by Default; IM8 Cloud Security (IaaS and PaaS): 1.5/S3, 1.5/S5, 1.6/S1h, 1.7/S23b; IM8 On-Premise IS (Non-S): 4.2/S1b |
| **ns-4** | Inter-Private Network Connectivity | Route network traffic between private networks without going through the internet. | Use CSP Private endpoint services (e.g., AWS PrivateLink with VPC endpoints) for unidirectional access to a specific service. Use VPC peering or Transit Gateway for layer-3 IP connectivity between VPCs. | When routing through the internet, there's an increased risk of man-in-the-middle and spoofing attacks. Bi-directional connectivity without fine-grained controls increases lateral exposure. | 1 | IM8 Cloud Security (IaaS and PaaS): 1.5/S7, 1.5/S4 |
| **ns-5** | Network and Application Layer Filtering | Filter direct traffic from the internet to protect against network and application layer attacks. | Deploy the following mechanisms as appropriate: Web Application Firewall (WAF); Distributed Denial of Service (DDoS) Protection (e.g., AWS Shield); Content Delivery Network (CDN) (e.g., CloudFront). | Lack of filtering for direct traffic from the internet exposes the system to the risk of network and application layer attacks, increasing the likelihood of DoS incidents and compromise of sensitive data. | 1 | IM8 Cloud Security (IaaS and PaaS): 1.5/S5; IM8 On-Premise ADS (Non-S): 1.1/S4 |
| **ns-6** | Valid and Trusted SSL/TLS Certificates | Ensure that deployed SSL/TLS certificates are signed by a trusted root CA, match the domain name, are not expired, and are not revoked. | Configure a certificate manager that auto-renews certificates and sends alerts before expiry (e.g., AWS Certificate Manager). | Using invalid SSL/TLS certificates introduces the risk of compromised encryption, man-in-the-middle attacks, and potential unauthorised access to sensitive information. | 1 | IM8 Cloud Security (IaaS and PaaS): 1.5/S8 |
| **ns-7** | Secure Inter-Service Communication | Ensure communications between services are secure by making them authenticated, authorised, and encrypted. | Design inter-service communications (e.g., databases, microservices) to be authenticated, authorised, and encrypted (e.g., via API gateways, proxies, private endpoint services, or service meshes). Log communication details. | Failure to ensure secure communications between services increases the risk of unauthorised access, data breaches, and potential manipulation of sensitive information during transit. | 1 | None |
| **ns-8** | Secure Cloud and On-Premises Connectivity | Route network traffic between on-premises systems and cloud systems through a secure intermediary. | Design secure communications to/from on-premises systems through a managed interface with boundary protection mechanisms (e.g., API gateways, application proxies, private endpoint services) rather than direct connectivity. | Insecure connectivity between cloud and on-premises environments can lead to data breaches, unauthorised access, and compromise of both cloud and on-premises resources. | 1 | None |

### 2.5 Backup & Recovery (br)
These controls establish resilience minimums, offsite rotation, and immutable backup parameters.

| ID | Title | Security Statement | Recommended Implementations & Actions | Risk / Rationale | Profile Level | References |
| :--- | :--- | :--- | :--- | :--- | :---: | :--- |
| **br-1** | Backup | Backup all important data and systems at least every 7 day(s), and store backups in a secure and separate location. | Use default CSP-managed backup services (e.g., AWS Backup, Azure Backup). Store backups and snapshots separately to primary data storage with data encrypted-at-rest. For SaaS, ensure vendor capability. | Without regular backups stored in a secure and separate location, there is an increased risk of data loss, system failures, and extended downtime. | 1 | MVSP 4.4: Backup and DR; IM8 Cloud Security (IaaS and PaaS): 1.2/S2; IM8 On-Premise IS (Non-S): 1.5/S1 |
| **br-2** | Recovery Testing | Conduct testing of recovery processes at least every 365 day(s) to ensure their effectiveness. | Ensure each test verifies the system's ability to fully restore all data and services. | Failure to regularly test recovery processes may result in ineffective response during actual incidents, increasing the risk of prolonged downtime and data loss. | 2 | MVSP 4.4: Backup and DR; IM8 Cloud Security (IaaS and PaaS): 1.2/S1d; IM8 On-Premise IS (Non-S): 1.5/S1d |
| **br-3** | Backup Retention | Prevent backups from being modified or deleted for 365 day(s) or as stipulated in the agency's data retention policies. | Use S3 Object Lock or Azure Blob Storage with immutability enabled to enforce time-based retention policies. | Lack of prevention measures against modification/deletion increases risk of data loss, ransomware lockouts, and inability to recover from security incidents. | 1 | MVSP 4.4: Backup and DR; IM8 Cloud Security (IaaS and PaaS): 1.2/S1b; IM8 On-Premise IS (Non-S): 1.5/S2c |

### 2.7 Logging & Monitoring (lm)
These controls establish tamper-resistant audit trails, alert configurations, database tracking, and log sanitization practices.

| ID | Title | Security Statement | Recommended Implementations & Actions | Risk / Rationale | Profile Level | References |
| :--- | :--- | :--- | :--- | :--- | :---: | :--- |

Un-scanned libraries expose applications to exploits. | 1 | MVSP 2.6: Dependency Patching; IM8 Cloud Security: 1.7/S8i; IM8 Cloud ADS: 8.1/S2, 6.1/S1c; IM8 On-Premise ADS: 1.1/S1i |
| **sd-6** | Secret Detection | Set up secret detection in the code repository and remediate true positives within 1 day(s). | Run automated secret scanning. Revoke and purge any accidentally exposed credentials immediately from the Git history. | Even if a secret is removed in a later commit, it remains retrievable in the Git history; immediate revocation is mandatory. | 1 | IM8 Cloud Security: 1.7/S8f; IM8 Cloud ADS: 1.1/S1f, 6.4/G1b; IM8 On-Premise ADS: 6.4/G1 |
| **sd-7** | CI Environment Variable Secrets Management | Protect environment variable secrets used in CI jobs by limiting them to protected pipelines and masking them in job logs. | Configure GitLab masked/protected variables or GitHub encrypted secrets.
